# RFD-006: Medusa Admin Access & Storefront Enablement Blockers

**Date:** 2025-11-20  
**Owner:** Codex (handoff to tiger team)  
**Status:** OPEN – Needs cross-team triage  
**Related:** RFD-005 (Admin auth), MIGRATION_PLAN Phase B2, docs/IMPLEMENTATION_GUIDE Milestones B2-B3

---

## Context

We attempted to finish Milestone **B2 (Single Product Import)** and unblock storefront integration per `docs/IMPLEMENTATION_GUIDE.md`. During execution we hit several platform-level failures that prevent completing the workflow, even though Medusa itself is reachable via `https://api.optic.works`.

The tiger team needs a consolidated view of the blockers so we can split ownership and resolve them in parallel. This RFD documents the current symptoms, reproduction steps, and proposed actions.

---

## Desired Workflows (Per B2/B3)

1. **Admin automation:** Scripts authenticate via secret key (preferred) or JWT fallback.
2. **Publishable key management:** `pnpm run setup:keys` creates/associates keys so Store API can be called.
3. **Catalog import verification:** `pnpm run catalog:import` + `pnpm run catalog:verify` prove Bed Presence Sensor exists in Medusa.
4. **Store API access:** `curl https://api.optic.works/store/products` works with publishable key header so storefront can consume real data.

As of 2025-11-20, only (1) and (3) succeed; (2) and (4) are blocking B2 completion.

---

## Issue 1 – Publishable API Key Endpoint Returns 404

**Symptom:** `pnpm run setup:keys` fails with `Cannot POST /admin/publishable-api-keys` even when authenticating with the secret API key.

```
cd services/medusa
MEDUSA_ADMIN_URL=https://api.optic.works \
MEDUSA_SECRET_KEY=sk_... \
pnpm run setup:keys

# Output (excerpt):
🔐 Resolving admin authentication...
✓ Using Medusa secret API key
📡 Fetching default sales channel...
✓ Found sales channel: "Default Sales Channel"
🔑 Creating publishable API key: "Storefront"...
✗ Failed to create publishable key: HTTP 404 - Cannot POST /admin/publishable-api-keys
```

**Notes**
- Hitting `GET https://api.optic.works/admin/publishable-api-keys` also returns 404, suggesting the admin route is not registered in this deployment.
- Without a publishable key we cannot hit `/store/*` endpoints or complete B2 exit criteria.

**Open Questions**
1. Is the Medusa backend missing the publishable API key module (e.g., workflows module disabled)?
2. Did the Cloudflare tunnel rewrite strip `/admin` routes beyond a specific allowlist?
3. Can the admin UI still create publishable keys manually? (UI access verification pending.)

---

## Issue 2 – Store API Requires Publishable Key We Cannot Mint

**Symptom:** Store API now enforces `x-publishable-api-key`, but since Issue #1 blocks key creation we cannot call `/store/products`.

```
curl -s https://api.optic.works/store/products
{"type":"not_allowed","message":"Publishable API key required ..."}

curl -s -H "x-publishable-api-key: pk_opticworks_2025_live_c9fa7e3575..." \
  https://api.optic.works/store/products
{"type":"not_allowed","message":"A valid publishable key is required ..."}
```

**Notes**
- The legacy key (`pk_opticworks_2025_live_c9fa7e...`) appears revoked or unlinked from default channel; there is no way to create/associate a replacement via scripts.
- This blocks Milestone B2 (“GET /store/products returns the imported product”) and any storefront testing.

**Next Steps**
1. Once Issue #1 is resolved, rerun `pnpm run setup:keys` to mint a new key and update Infisical.
2. If the endpoint stays 404, we need an alternative method (database migration, manual admin UI path, or Medusa upgrade) to provision publishable keys.

---

## Immediate Actions for Tiger Team

1. **Verify Admin Routes** – Inspect the Medusa deployment to confirm whether `/admin/publishable-api-keys` exists. This may require pulling `services/medusa` on Hetzner and hitting the route locally to rule out Cloudflare interference.
2. **Check Medusa Modules** – Ensure the publishable key functionality is enabled for Medusa v2.11 (may require installing the workflows module or upgrading Medusa).
3. **Manual UI Test** – From `https://api.optic.works/app`, attempt to create a publishable key and copy the full secret before navigating away. If the UI succeeds, document the steps and add the key to Infisical as a temporary unblock.
4. **Update Docs** – Once a working flow is found, update Milestone B2 instructions in `docs/IMPLEMENTATION_GUIDE.md` to reflect reality (secret key usage, admin UI steps, script commands).
5. **Keep JWT Bug Escalation Open** – Continue tracking the `actor_id` issue with Medusa core so we can restore JWT fallback once publishable key routes are stable.

## Definition of Done (to close RFD-006)

1. `pnpm run setup:keys` completes successfully against `https://api.optic.works`.
2. A new publishable key exists in Infisical, linked to the default sales channel.
3. `curl -H "x-publishable-api-key: <new-key>" https://api.optic.works/store/products` returns the imported catalog.
4. Milestone B2 exit criteria are satisfied and documented, so storefront work can resume.
5. Follow-up tasks (JWT fix, automation hardening) tracked either here or in RFD-005 as appropriate.
