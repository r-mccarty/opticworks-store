# RFD-005: Phase 2 (B2) Admin API Authentication Blockers

## Context
Stage B2 of the migration plan requires importing at least one live product into the Hetzner Medusa instance and validating the workflow end-to-end through the storefront and admin dashboard. The automation scripts in `services/medusa/scripts/*` assume we can hit the Medusa Admin API with an `Authorization: Bearer <MEDUSA_ADMIN_TOKEN>` header.

While verifying the Hetzner node (`ssh hetzner-node`) we confirmed:
-
  `curl https://api.optic.works/health` and `curl http://localhost:9000/health` both return `200 OK`.
-
  PM2 shows `medusa-dev` running and Postgres contains all core tables plus the publishable API key (`pk_opticworks_2025_live_c9…`).
-
  `pnpm medusa user --email admin@opticworks.io --password OpticWorks2025!` succeeds and inserts a second admin record.

Despite that baseline, any attempt to authorize against `/admin/*` returns `{"message":"Unauthorized"}`. This blocks B2 entirely.

## Observed Issues

1. **Admin API rejects MEDUSA_ADMIN_TOKEN**
   - `curl -H "Authorization: Bearer $MEDUSA_ADMIN_TOKEN" http://localhost:9000/admin/sales-channels` and the same request through `https://api.optic.works` both 401.
   - The token in `/opt/opticworks/medusa-backend/services/medusa/.env` matches the value stored in Postgres (`api_key` table) and the script-created row looks correct (`type='secret'`, `redacted='adm_OpticWorks'`), but the HTTP middleware never recognizes it.
   - Trying the Medusa SDK header names (`x-medusa-access-token`) yields the same 401.

2. **Admin user login no longer matches CLI expectations**
   - Even after minting `admin@opticworks.io` via `pnpm medusa user`, calls to `/admin/auth/token` with that email/password still 401.
   - The Admin UI at `https://api.optic.works/app` loads, but logging in throws “Unauthorized” immediately, suggesting the deployed stack expects a different auth provider (e.g., new auth module + OTP) than what the scripts assume.

3. **Automation scripts (publishable key + catalog import) are hard-blocked**
   - `pnpm run setup:keys` cannot fetch `/admin/sales-channels` so it fails before doing any work.
   - `pnpm run catalog:import` and `pnpm run catalog:verify` bail out for the same reason.
   - Without programmatic admin access we cannot satisfy the B2 exit criteria (import product, verify via admin, use same variant in cart API).

4. **No documented path for secret API key creation in Medusa v2**
   - RFD-004 solved the RFD-003 publishable key gap by scripting `/admin/publishable-api-keys`.
   - Medusa v2 now stores “secret” keys differently and the framework-provided auth middleware expects tokens issued via the new `/settings/secret-api-keys` UI. There is no CLI or script capturing that process, and the schema insert we attempted still fails to authenticate.

## Impact
- Stage B2 is fully blocked; the storefront still falls back to `src/lib/products.ts` because we cannot prove a single product exists in Medusa.
- All downstream automation (`catalog:import`, `catalog:verify`, smoke tests, Infisical wiring) depends on having an admin bearer token. Without it we cannot flip `NEXT_PUBLIC_MEDUSA_ENABLED=true` confidently.
- The Cloudflare Access work (Phase “Security Hardening”) cannot start because we cannot even reach the admin API without bypassing auth.
- Team members risk spending hours debugging scripts when the underlying issue is missing/undocumented auth flows.

## Technical Lead Response (2025-11-18)

**TL;DR**: The automation scripts are based on a fundamental misunderstanding of how Medusa v2 authentication works. The `MEDUSA_ADMIN_TOKEN` environment variable is **not** a bearer token that can be used directly with the Admin API. You must authenticate via the login endpoint to obtain a JWT token. All observed issues stem from this misconception.

### Root Cause Analysis

#### Issue #1: Misunderstanding of `MEDUSA_ADMIN_TOKEN`

**What you thought**: `MEDUSA_ADMIN_TOKEN` is a static bearer token that can be used directly in `Authorization: Bearer <token>` headers.

**Reality**: In Medusa v2, there is **no such thing** as a static admin bearer token that works this way. The `MEDUSA_ADMIN_TOKEN` variable you generated is not a recognized Medusa authentication mechanism.

**How Medusa v2 actually works**: There are three supported authentication methods:

1. **JWT Token Authentication** (recommended for automation):
   - Login via `POST /auth/admin/emailpass` with email/password
   - Receive a JWT token in the response
   - Use that JWT token in `Authorization: Bearer <jwt_token>` for subsequent requests
   - Tokens expire (typically 24h), requiring re-authentication

2. **API Key Authentication** (best for long-lived automation):
   - Create a secret API key through the Admin Dashboard UI (`/app`)
   - Navigate to Settings → API Key Management → Create API Key
   - Use the key in `Authorization: Basic <api_key>` headers
   - Keys don't expire unless explicitly revoked

3. **Cookie Session Authentication**:
   - Used by the Admin Dashboard frontend
   - Not suitable for automation scripts

#### Issue #2: Why Your Tests Failed

**Test**: `curl -H "Authorization: Bearer $MEDUSA_ADMIN_TOKEN" http://localhost:9000/admin/sales-channels`
**Result**: 401 Unauthorized
**Why**: Medusa v2 doesn't recognize arbitrary bearer tokens. It only accepts:
- Valid JWT tokens obtained from `/auth/admin/emailpass`
- Secret API keys (in `Authorization: Basic` header, not `Bearer`)

**Test**: `curl /admin/auth/token` with email/password
**Result**: 404 (endpoint doesn't exist)
**Why**: The correct endpoint is `/auth/admin/emailpass`, not `/admin/auth/token`

**Test**: Login via Admin UI at `https://api.optic.works/app`
**Result**: "Unauthorized"
**Why**: This is likely a separate issue. The emailpass auth provider is built-in by default, so if the UI login fails, it suggests:
- CORS configuration issue (check `MEDUSA_ADMIN_CORS` in `.env`)
- The admin user wasn't created properly
- JWT/Cookie secrets are misconfigured

### Technical Decisions & Solutions

#### Decision 1: Authentication Strategy for Automation Scripts

**Rejected Approach**: Continue trying to use a static `MEDUSA_ADMIN_TOKEN`
- Not supported by Medusa v2 architecture
- Would require custom middleware development
- Maintenance burden

**Approved Approach**: Two-tier authentication system

**Tier 1** - Local development & CI/CD (short-lived access):
- Scripts authenticate via `/auth/admin/emailpass` at runtime
- Store admin email/password in `.env` (or Infisical)
- Obtain JWT token programmatically before each script run
- Accept token expiration as normal behavior

**Tier 2** - Production automation (long-lived access):
- Create a secret API key through the Admin Dashboard
- Store the key in Infisical
- Use API key for all production automation
- Rotate keys quarterly or when team members leave

#### Decision 2: Correct Admin Login Endpoint

The correct authentication endpoint is:

```bash
POST /auth/admin/emailpass
Content-Type: application/json

{
  "email": "admin@opticworks.io",
  "password": "OpticWorks2025!"
}
```

**Expected Response** (200 OK):
```json
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}
```

**Usage**:
```bash
# Get JWT token
TOKEN=$(curl -X POST http://localhost:9000/auth/admin/emailpass \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@opticworks.io","password":"OpticWorks2025!"}' \
  | jq -r '.token')

# Use token for authenticated requests
curl -H "Authorization: Bearer $TOKEN" \
  http://localhost:9000/admin/sales-channels
```

#### Decision 3: Script Architecture Updates Required

All automation scripts need to be updated with an authentication helper:

**New file**: `services/medusa/scripts/utils/auth.ts`

```typescript
/**
 * Admin Authentication Utility
 *
 * Handles JWT token acquisition for automation scripts.
 * Addresses RFD-005: Correct Medusa v2 authentication flow
 */

export interface AuthCredentials {
  email: string;
  password: string;
}

export interface AuthToken {
  token: string;
  expiresAt?: string;
}

/**
 * Authenticate and obtain JWT token
 */
export async function getAdminToken(
  adminUrl: string,
  credentials: AuthCredentials
): Promise<string> {
  const response = await fetch(`${adminUrl}/auth/admin/emailpass`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
    },
    body: JSON.stringify(credentials),
  });

  if (!response.ok) {
    const text = await response.text();
    throw new Error(
      `Admin authentication failed: HTTP ${response.status} - ${text}\n` +
      `Ensure admin user exists: pnpm medusa user -e ${credentials.email} -p <password>`
    );
  }

  const data = await response.json() as AuthToken;

  if (!data.token) {
    throw new Error('Authentication response missing token field');
  }

  return data.token;
}

/**
 * Get admin credentials from environment
 */
export function getAdminCredentials(): AuthCredentials {
  const email = process.env.MEDUSA_ADMIN_EMAIL || 'admin@optic.works';
  const password = process.env.MEDUSA_ADMIN_PASSWORD;

  if (!password) {
    throw new Error(
      'MEDUSA_ADMIN_PASSWORD not set in environment.\n' +
      'Add to .env or Infisical:\n' +
      '  MEDUSA_ADMIN_EMAIL=admin@optic.works\n' +
      '  MEDUSA_ADMIN_PASSWORD=<your-password>'
    );
  }

  return { email, password };
}
```
