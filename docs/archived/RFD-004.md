# RFD-004: Medusa Migration Workflow Risks

## Context
While attempting to begin the storefront → Medusa migration, several workflow blockers surfaced around the Medusa developer environment. These issues prevent us from reliably standing up the backend needed to replace the static catalog / checkout.

## Observed Issues

1. **Medusa dev server instability**
   - Running `pnpm dev` under `services/medusa/` routinely crashes with esbuild stack traces (`@medusajs/admin-bundler → esbuild`). The server restarts immediately, closing open connections and making API calls from scripts unreliable.

2. **Admin build requirement for `pnpm start`**
   - Attempting a production start (`pnpm start`) fails with “Could not find index.html in the admin build directory. Make sure to run `medusa build`”. We need a documented `pnpm build` step (and its prerequisites) before we can host the service in prod mode.

3. **Fetch/connection inconsistencies**
   - `curl http://127.0.0.1:9000/store/products` succeeds, but Node’s `fetch` (used by import scripts) intermittently returns `ECONNREFUSED`. The importer and other automation cannot rely on the service remaining reachable.

4. **Missing publishable key + sales channel wiring**
   - The store API rejects requests until a publishable key is created, associated to a sales channel, and passed via `x-publishable-api-key`. There’s no script/automation for this yet.

5. **Catalog importer incompatibilities**
   - `services/medusa/scripts/import-products.ts` needed multiple fixes:
     - Admin API expects `sales_channels`, `options`, and option values per variant; the script previously sent `product` wrappers with `id`s.
     - Even after adjustments, the importer still depends on the Medusa server staying up during the entire run (see issue #1/3).

6. **Hetzner provisioning gaps**
   - The remote VM lacked Git/node/pnpm/Postgres/Redis; bringing it up was manual. Future contributors need a runbook (or automation) to bootstrap the node quickly.

## Impact
- Without a stable Medusa instance, we can’t flip the storefront to live data, nor can we run migration scripts or populate the catalog.
- CI/E2E efforts (Playwright, etc.) can’t target Medusa because the API endpoints are unreliable.
- Developers spend time re-provisioning the backend instead of working on storefront changes.

## Recommended Actions
1. **Document a supported environment**
   - Capture the exact node/pnpm version, required system packages, and the authoritative steps to run Postgres/Redis locally or on Hetzner.

2. **Add automation**
   - Provide a script (Makefile or npm script) that runs `pnpm dev` inside a supervisor (forever/pm2) or Docker so the service survives CLI crashes.
   - Add a helper script to create the default publishable key + sales channel association.

3. **Stabilize import tooling**
   - Finish hardening `import-products.ts` (now option-aware) and wrap it in a CLI that retries transient failures and reports successes/failures clearly.

4. **Verify admin bundler**
   - Investigate why `@medusajs/admin-bundler` → esbuild panics when we edit TypeScript in `services/medusa`. We may need to pin esbuild, update Node flags, or prebuild the admin UI to avoid watch-mode crashes.

Tracking these items in RFD-004 keeps the migration plan honest—until they’re addressed, wiring the storefront directly to Medusa will remain brittle. Add follow-up tasks/issues referencing this RFD as fixes land.
