# Medusa v2 Stripe Tax Integration: Audit and Migration Roadmap

## Current Architecture & Issues

**System Overview:** The OpticWorks store uses a **Medusa v2 backend** (Node.js, PostgreSQL, Redis) with a **Next.js 15 frontend** (deployed on Cloudflare Workers). Key integrations include Stripe for payments (and Stripe Tax for automated sales tax), a custom EasyPost fulfillment provider for shipping rates/labels, Cloudflare Tunnel for API access, and Resend for transactional emails[\[1\]](file://file_000000000e98720c8b4a62fdde699839#:~:text=%2B,v)[\[2\]](file://file_000000000e98720c8b4a62fdde699839#:~:text=,). The frontend communicates with Medusa’s Store APIs using a publishable key and a base URL pointing to the Cloudflare tunnel[\[3\]](file://file_000000000e98720c8b4a62fdde699839#:~:text=).

**End-to-End Flow:** In the current setup, customers can add items to a cart, input their address and select shipping, see taxes and totals, then pay via Stripe. The flow involves multiple moving parts:

* **Cart & State:** The frontend maintains cart state in a local Zustand store (for optimistic updates) synchronized with the Medusa cart via its REST API[\[4\]](file://file_0000000005bc722f8de4eb7ce1ca362e#:~:text=)[\[5\]](file://file_0000000005bc722f8de4eb7ce1ca362e#:~:text=,local%20%2B%20reset%20cartId). This hybrid approach (local state \+ server state) has introduced complexity in keeping the frontend **“proper state”** in sync with the backend. For example, a hydration guard was needed to avoid SSR mismatch because the cart is stored in localStorage on the client[\[6\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=const%20,Loading%20%2F%3E%3B).

* **Shipping Rates:** Initially, shipping rate calculation was done entirely in the frontend (calling EasyPost directly from the client). This led to **“split-brain”** logic and even an **infinite loop bug** due to complex state updates triggering repeated API calls[\[7\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=6,Resolved). That bug maxed out request limits and was fixed by migrating shipping calculation to a **Medusa fulfillment provider** on the backend[\[8\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=The%20previous%20storefront,out%20Cloudflare%20Workers%20request%20limits). Now, the frontend simply requests shipping options from Medusa and then calls a calculate endpoint for real-time rates[\[9\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=,Returns%20actual%20price%20from%20provider). This aligns better with Medusa’s design (fulfillment logic in backend) and avoids exposing API keys or duplicating logic in the client[\[10\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=,backend%2C%20not%20exposed%20to%20Workers).

* **Stripe Tax Integration:** A custom Medusa **tax provider** (stripe-tax) handles tax calculation by calling Stripe’s Tax API on each cart update[\[11\]](file://file_000000001078720c85dc537ad8139c14#:~:text=1.%20,placed%2C%20populating%20Stripe%20Tax%20reports)[\[12\]](file://file_000000001078720c85dc537ad8139c14#:~:text=3.%20,response%20to%20Medusa%20tax%20lines). Medusa’s tax module invokes this provider whenever a shipping address is added or changed. **However, by design Medusa calls the tax provider twice** – once for line items and once for the shipping line[\[13\]](file://file_000000001078720c85dc537ad8139c14#:~:text=Separate%20Item%20and%20Shipping%20Calls). In a canonical tax calculation (e.g. Avalara), items and shipping should be taxed together in a single calculation. The current Stripe Tax integration works around this Medusa quirk by returning an empty array on the “shipping-only” call, since Stripe’s API cannot calculate shipping tax in isolation[\[14\]](file://file_000000001078720c85dc537ad8139c14#:~:text=%60%60%60%20Call%201%3A%20getTaxLines%28items%3D,product%20tax%2C%20return%20tax%20lines)[\[15\]](file://file_000000001078720c85dc537ad8139c14#:~:text=We%20return%20empty%20array%20for,be%20calculated%20with%20the%20items). While functional, this double-call pattern is considered an **anti-pattern** because it’s inefficient and forces awkward handling in the provider code.

* **Order Completion:** The payment flow uses Stripe’s **Deferred Intent** pattern – the Stripe Elements are initialized with an amount (cart subtotal) but **no PaymentIntent is confirmed until after shipping is applied**. Once the user selects a shipping method (which updates the cart’s total including tax and shipping), the frontend updates the Stripe Elements amount and then confirms the payment[\[16\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=1.%20,commit%60%20subscriber%20commits%20transaction%20to). Medusa’s payment collection API is used to create a Stripe PaymentIntent under the hood, and the final completeCart() call converts the cart to an order after successful payment[\[17\]](file://file_00000000a6a8722fae796b92119c5d66#:~:text=%60%60%60typescript%20const%20,redirect%3A%20%27if_required%27%2C)[\[18\]](file://file_00000000a6a8722fae796b92119c5d66#:~:text=if%20%28paymentIntent%3F.status%20%3D%3D%3D%20%27succeeded%27%29%20,). A known issue here is that if the cart completion fails (e.g. network hiccup) after Stripe already charged the card, the frontend currently employs a **fallback workaround**: it shows a “Finalizing your order...” message and then forces a redirect to the success page after 2 seconds[\[19\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=%60%60%60typescript%20%7D%20catch%20%28completeError%29%20,paymentIntent.id%7D%60%3B%20%7D%2C%202000%29%3B). This relies on the Stripe webhook (via Hookdeck) to eventually create the order in Medusa asynchronously. While this ensures the user isn’t stuck indefinitely, it’s a **hacky fallback** rather than a robust solution.

**Summary of Issues:** In the current codebase, a few patterns stand out as non-canonical or problematic:

* **Split Logic Between Frontend & Backend:** Some business logic and state (especially around checkout, shipping, and possibly tax display) are duplicated or handled in both the frontend and backend, leading to extra complexity. The previous fully-frontend approach left behind vestigial code and state management that may no longer be needed or that conflicts with the new backend-driven approach.

* **Multiple API Calls for Taxes and Shipping:** The Stripe Tax provider is invoked twice per update (products vs. shipping) due to Medusa’s internal flow[\[13\]](file://file_000000001078720c85dc537ad8139c14#:~:text=Separate%20Item%20and%20Shipping%20Calls). Similarly, retrieving shipping rates requires an extra loop of API calls (list options then calculate each)[\[9\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=,Returns%20actual%20price%20from%20provider). These are seen as anti-patterns compared to a more unified calculation call.

* **Workarounds and Kludges:** The codebase includes several **kludges** to patch over edge cases – e.g. the cart hydration guard for SSR[\[6\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=const%20,Loading%20%2F%3E%3B), the payment completion timeout redirect[\[19\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=%60%60%60typescript%20%7D%20catch%20%28completeError%29%20,paymentIntent.id%7D%60%3B%20%7D%2C%202000%29%3B), and previously the 20-second test delay for the pay button[\[20\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=1.%2020,E2E%20Tests). These indicate areas where the architecture could be improved so such fallbacks aren’t necessary.

In summary, the current implementation **functions end-to-end** – orders can be placed with correct tax, shipping, and payment, and emails and labels are generated – but it does so with some architectural debt. The goal is to **refactor towards a canonical Medusa architecture**, similar to how the **Avalara tax integration** is designed, eliminating redundant frontend logic and relying on Medusa’s backend for all commerce calculations and state.

## Canonical Medusa Architecture (Avalara Example)

Medusa’s official approach to extensibility is to keep commerce logic on the **backend**, using the modular architecture for taxes, fulfillment, payments, etc., and have the frontend interact with those via clean APIs. The Avalara integration example is instructive:

* **Tax Calculation via Provider:** Medusa’s Tax Module allows third-party tax providers (like Avalara or Stripe Tax) to plug in. During checkout, Medusa will use the configured provider to calculate taxes for the cart’s line items and shipping **automatically**, and then apply those taxes to the cart totals[\[21\]](https://medusajs.com/blog/avalara-integration/#:~:text=Tax%20Calculation%20with%20Avalara). The expectation is that **the frontend does not calculate taxes itself** – it simply triggers the normal cart update flow (e.g. adding an address or changing items) and Medusa returns tax-inclusive totals. In the Avalara tutorial, a custom provider is implemented to call Avalara’s API for tax rates, just as we have done for Stripe Tax.

* **Order Placement & Tax Commit:** With Avalara, Medusa’s event system is used to **create a transaction in Avalara when an order is placed**[\[22\]](https://medusajs.com/blog/avalara-integration/#:~:text=Medusa%E2%80%99s%20events%20and%20orchestration%20systems,time%20an%20order%20is%20placed)[\[23\]](https://medusajs.com/blog/avalara-integration/#:~:text=export%20const%20config%3A%20SubscriberConfig%20%3D,). This parallels our Stripe Tax “commit” subscriber, which calls transactions.createFromCalculation() on Stripe’s API after an order is completed[\[24\]](file://file_000000001078720c85dc537ad8139c14)[\[25\]](file://file_000000001078720c85dc537ad8139c14#:~:text=%E2%94%82%20%20Commit%20Subscriber%3A%20,%E2%94%82). The canonical pattern is to use an **event subscriber (order.placed)** or a workflow to handle any post-order external side effects, rather than doing so in the request/response cycle of checkout. We have followed this pattern with our stripe-tax-commit subscriber – which is good – ensuring the tax reporting call is decoupled from the user-facing checkout flow.

* **Fulfillment via Provider:** Similarly, Medusa encourages implementing a **Fulfillment Provider** for shipping logic (as done for Avalara, TaxJar, and in our case EasyPost). The shipping rates calculation and label purchase happen on the backend, triggered by API calls from the frontend, which is exactly what our EasyPost module does now. This is considered best practice because it centralizes shipping logic in the backend (for reliability, admin visibility, and security of API keys)[\[26\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=,backend%2C%20not%20exposed%20to%20Workers).

* **Frontend’s Role:** In a canonical headless setup, the Next.js storefront should primarily handle **presentation and user input**. It should collect user data (e.g. address, payment info via Stripe Elements) and call the Medusa backend’s Store APIs (e.g. update cart address, add shipping method, create payment session). The frontend should **not implement commerce rules** itself. For example, instead of calculating totals or taxes, it should trust the values returned by Medusa. This simplifies the client and avoids the “split-brain” scenario where the front and back have to mirror each other’s logic.

* **State Management:** Medusa’s own starter storefront uses tools like TanStack Query (react-query) or SWR to fetch data from the backend and cache it, rather than maintaining a complex client-side domain model. Our current use of Zustand for cart is functional, but we must ensure it’s not duplicating too much logic. Ideally, the **source of truth** for cart contents and totals is the Medusa backend – the client store can cache this but should refresh from the server after any critical change (add item, set address, etc.). Persisting minimal state (like cart ID, or an optimistic item list) is fine, but anything that the backend ultimately decides (pricing, stock availability, tax, shipping cost) should come from the backend response.

In short, the **target architecture** is one where the **Medusa backend handles all business logic** (tax calculation, shipping rates, payment intent creation, order creation, email sending), and the Next.js frontend is a thin layer that just orchestrates user interactions and displays the results from Medusa. This avoids inconsistent states and errors that arise from duplicating logic. The Avalara integration demonstrates how a third-party service can be cleanly integrated into Medusa’s workflow without breaking this separation of concerns.

## Audit Findings vs. Medusa Docs

Comparing our codebase to Medusa’s official documentation and patterns reveals several gaps to address:

* **Tax Calculation “Double Call”:** Medusa’s tax module currently invokes TaxProviderService.getTaxLines() twice (once for line items, once for shipping) instead of a single consolidated call[\[13\]](file://file_000000001078720c85dc537ad8139c14#:~:text=Separate%20Item%20and%20Shipping%20Calls). This is a Medusa internal behavior, not something we introduced. In our Stripe Tax provider, we handle it by returning no tax lines on the shipping-only invocation[\[14\]](file://file_000000001078720c85dc537ad8139c14#:~:text=%60%60%60%20Call%201%3A%20getTaxLines%28items%3D,product%20tax%2C%20return%20tax%20lines). While this workaround is necessary given Medusa’s flow, it’s documented as a limitation[\[27\]](file://file_000000001078720c85dc537ad8139c14#:~:text=metadata,field). **Canonical Medusa** (exemplified by Avalara) has the same pattern – Avalara’s provider would also be called twice – so our implementation is actually consistent with Medusa’s current design. However, from an architecture standpoint, a single tax calculation with both items and shipping is preferable. We should keep an eye on Medusa’s updates or consider contributing a change to allow combined tax calculation. For now, this is a **known quirk** rather than a misimplementation.

* **Redundant Frontend State Logic:** The earlier all-frontend checkout flow likely left behind code that is now redundant. For example, before adopting the Medusa tax provider, we might have attempted to use Stripe.js on the frontend to calculate taxes, or computed totals in the client. Now that tax and shipping are handled by Medusa, any such code should be removed. The **CheckoutState store** (useCheckoutState) still holds a taxAmount and subtotal in state[\[28\]](file://file_0000000005bc722f8de4eb7ce1ca362e#:~:text=%60%60%60typescript%20interface%20CheckoutState%20,), which are updated when shipping is selected and the cart is refetched[\[29\]](file://file_000000001078720c85dc537ad8139c14#:~:text=1.%20,tax%20in%20Order%20Summary%20section)[\[30\]](file://file_000000001078720c85dc537ad8139c14#:~:text=Tax%20is%20fetched%20after%20shipping,Updates%20%60taxAmount%60%20state). This isn’t inherently wrong – the frontend needs to show the tax in the UI – but it’s effectively duplicating values already in the Medusa cart. We should ensure that **CheckoutState is only used for temporary UI state** and not doing any calculations on its own. Audit if any calculations of total or tax happen in the frontend code (they shouldn’t beyond simple addition of subtotals which Medusa also provides).

* **Frontend Calling Backend Appropriately:** In some places, our frontend might be doing things in a roundabout way. For instance, the login/logout via Next.js API routes (proxying to Medusa) is fine for handling cookies, but for other operations we might simplify by calling Medusa Store endpoints directly. The Next.js Starter uses direct fetches to Medusa’s API with proper CORS/POS headers. Using our Cloudflare Tunnel (api.optic.works) is already in place, so that’s good[\[31\]](file://file_000000000e98720c8b4a62fdde699839#:~:text=Hostnames). We just need to verify that **every significant state change (cart updates, applying discounts, etc.) goes through the Medusa API**, not local mutations only.

* **Workaround \#1: Payment Completion Fallback:** The snippet in our CheckoutForm that catches an error from completeCart() and then does a setTimeout redirect[\[19\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=%60%60%60typescript%20%7D%20catch%20%28completeError%29%20,paymentIntent.id%7D%60%3B%20%7D%2C%202000%29%3B) is an **anti-pattern** because it’s essentially guessing that the order will be completed soon. Official Medusa docs don’t provide a pattern for this scenario (it’s an edge case arising from network issues), but a more robust solution would be to **poll the backend** for the order status or rely on the webhook in a safer way. We should remove the hardcoded timeout and implement a strategy where, if completeCart fails but the payment was successful, the frontend can periodically check (e.g. every 2-3 seconds) whether an order has appeared for that cart or PaymentIntent. Once detected (or after a reasonable timeout with no order), respond accordingly (navigate to success page or show an error/support message). This way, we avoid a blind redirect and provide better feedback. The canonical architecture would treat order finalization as something that might happen asynchronously (via webhook) and handle it gracefully.

* **Workaround \#2: Hydration Guard:** The hydration mismatch guard in CartPage (delaying rendering until mounted) is a known fix for using client-side cart data[\[6\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=const%20,Loading%20%2F%3E%3B). While it works, it indicates our state management might not be optimal. A canonical approach could be to **load the cart server-side** (e.g. via getServerSideProps or using Next.js App Router data fetching) so the initial HTML already reflects the cart contents, avoiding the need for this guard. Because we deploy on Cloudflare Workers, SSR can be tricky (our Cloudflare Worker can call the Medusa API via medusa.optic.works bypass URL[\[2\]](file://file_000000000e98720c8b4a62fdde699839#:~:text=,), which is good). Implementing SSR cart loading would remove the need for the hydration hack and make the app faster for users (less loading spinners). This refactor can be part of our roadmap, ensuring the frontend always has up-to-date data from the backend without flash-of-empty-cart issues.

* **State Synchronization Issues:** We should audit if there are any remaining cases where the frontend state could get out of sync. For example, if a user is on the checkout page and shipping options are fetched, is the cart (and thus tax) updated in one atomic step? Our **Tax Flow** documentation confirms the sequence: user enters address, selects shipping, then we fetch the updated cart which includes the tax\_total calculated by Stripe Tax, and update the UI[\[16\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=1.%20,commit%60%20subscriber%20commits%20transaction%20to). This indicates the front-end is correctly relying on the backend for the new totals at that point. We just need to ensure that this pattern is used everywhere: **whenever something changes that affects totals (adding a discount, changing quantity, etc.), we refresh from the backend** so that taxes and other computed fields are accurate. The Medusa backend should be the source of truth for any derived values.

* **Resend Email Integration:** The codebase integrates Resend for transactional emails (order confirmations, etc.). Ideally, this is done via a Medusa subscriber or workflow on the backend (e.g. listening for order.placed or order.shipment\_created events). We should verify that the email sending is triggered server-side and not, for example, waiting on any frontend action. As long as it’s implemented as a Medusa module or subscriber, it aligns with canonical design (the frontend should not attempt to send emails). This likely is already the case (since Resend API keys would be secret). No changes needed if it’s correctly hooked into Medusa’s event system.

In summary, the audit finds that **most core logic is already in the backend** (thanks to the custom Stripe Tax and EasyPost modules), which is good. The main issues are residual complexity in the frontend from earlier approaches and a few hacky solutions to edge cases. The migration should focus on **cleaning up the frontend**, ensuring a single source of truth for all data, and aligning closely with Medusa’s documented best practices for a “clean” separation of concerns.

## Roadmap to a Canonical Architecture

To transition the codebase to a more **sensible, canonical architecture** without workarounds or anti-patterns, we propose the following steps:

**1\. Simplify Frontend State Management:**  
Audit the Next.js storefront for any redundant state logic that duplicates backend functionality. In particular:

* **Cart State:** Consider relying more on direct Medusa API responses for cart content and totals instead of maintaining full copies in Zustand. We can still use Zustand or React Context to store the cart ID and optimistic updates, but after any operation (adding/removing items, applying a coupon, etc.), fetch the updated cart from Medusa to sync actual totals (Medusa will have applied taxes, discounts, etc.). This ensures the **Medusa backend is the single source of truth** for pricing. If our useCart store already does this (it calls syncWithMedusa() after mutations[\[5\]](file://file_0000000005bc722f8de4eb7ce1ca362e#:~:text=,local%20%2B%20reset%20cartId)), ensure there’s no path that bypasses it. Remove any code that manually recalculates totals on the client.

* **Checkout State:** Verify that useCheckoutState().taxAmount and total are always derived from the Medusa cart data[\[29\]](file://file_000000001078720c85dc537ad8139c14#:~:text=1.%20,tax%20in%20Order%20Summary%20section)[\[32\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=2.%20,transaction%20to%20Stripe%20Tax%20dashboard). If any calculations exist (e.g. summing subtotal \+ tax \+ shipping on the frontend), replace them by using cart.total or similar fields from the API. The frontend’s job should just be to display those values. We can eliminate taxAmount from Zustand if we instead directly use cart.tax\_total from the fetched cart object. In React, this could mean passing the cart data down to components instead of storing parts of it separately.

* **Remove Leftover Client Logic:** Search the frontend code for any direct calls to Stripe’s Tax or EasyPost APIs (there should be none after our migration, but double-check). Also remove any “manual” tax or shipping computations. For example, if earlier code was setting a tax estimate based on region or doing client-side address validation, prefer to let Medusa and our backend providers handle it. The **split-brain scenario** (where both front and back try to handle the same logic) should be resolved by **dedicating all such logic to the backend**.

* **Use Official Patterns:** Optionally, consider incorporating patterns from Medusa’s Next.js Starter. For instance, using React Query to fetch the cart (/store/carts/{id}) and have it update automatically will simplify state sync. This isn’t required, but it’s a proven approach. At minimum, ensure our custom state management doesn’t conflict with how Medusa expects things (for example, do we properly handle guest cart vs logged-in cart? Medusa uses cart ID either way, so just ensure the ID is stored consistently and cleared on logout or order completion).

**2\. Refine Stripe Tax Integration:**  
Our Stripe Tax provider is already modeled on the Avalara example (custom provider \+ commit subscriber). To make it truly canonical:

* **Accept the Double-Call Pattern (for now):** Since Medusa calls getTaxLines twice, continue to handle the shipping call gracefully (return empty array) as we do now[\[15\]](file://file_000000001078720c85dc537ad8139c14#:~:text=We%20return%20empty%20array%20for,be%20calculated%20with%20the%20items). Document this clearly in the code as a Medusa limitation. This avoids any unexpected behavior and is aligned with how other tax providers (like Avalara) would function. In the future, watch Medusa’s releases or RFCs for any improvement to tax calculation strategies that might allow combining calls. If an update allows us to get both line item and shipping taxes in one go, update the provider accordingly. Until then, our implementation is as canonical as it can be under the hood.

* **Ensure Proper Region Configuration:** Double-check that all regions in Medusa are configured to use our stripe-tax provider (the provider ID should be tp\_stripe-tax\_stripe-tax)[\[33\]](file://file_000000001078720c85dc537ad8139c14#:~:text=Tax%20regions%20must%20be%20configured,id)[\[34\]](file://file_000000001078720c85dc537ad8139c14#:~:text=country_code%3A%20,). A common pitfall is a region not attached to the custom provider, resulting in tax\_total: 0[\[35\]](file://file_000000001078720c85dc537ad8139c14#:~:text=,Ensure). Our code seems to handle this via seeding, but it’s worth auditing against Medusa docs to ensure consistency.

* **No Frontend Tax Logic:** Confirm that the frontend is **not calling Stripe’s tax APIs directly** at any point. The Stripe Tax **AddressElement** is used purely for address input UI (which is fine), but the actual tax calculation should only occur in the Medusa backend. From our docs, this is the case: after selecting shipping, the frontend calls getCart() and receives the tax\_total from Medusa[\[32\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=2.%20,transaction%20to%20Stripe%20Tax%20dashboard). Keep this pattern. If any team members in the future suggest calculating tax on the client (for faster UI updates), resist that in favor of Medusa’s official flow. Medusa’s automatic tax ensures the cart always has the correct tax based on the latest address and items.

* **Stripe Tax Commit Workflow:** Our subscriber that commits taxes to Stripe after order placement should be reviewed for idempotency and error handling. According to our docs, it already checks for existing transactions and treats that as success[\[36\]](file://file_000000001078720c85dc537ad8139c14#:~:text=1.%20,fires). This is good. To be fully robust, consider what happens if the subscriber fails (e.g., network error to Stripe) – Medusa’s event system might allow retry or at least logs it. As part of canonical architecture, such side-effects should not affect the order completion for the customer (which they don’t in our case, since it’s async). Just ensure logs or alerts are in place for failures, so we can manually reconcile if needed. This aligns with the Avalara approach of using workflows to handle external calls without impacting the main transaction.

**3\. Consolidate Shipping & Fulfillment Logic:**  
We’ve already moved shipping rate calculation to the backend via the EasyPost provider, which is a big win. To further canonize this:

* **Clean Up Frontend Shipping Code:** Remove any of the old “frontend shipping” code that was replaced. For example, if there are leftover components or utils that attempted to calculate shipping or select shipping rates outside of Medusa’s context, delete them. Our useMedusaShipping hook now calls the Medusa endpoints (/shipping-options and /shipping-options/{id}/calculate) as required[\[37\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=%2A%2AWhat%2A%2A%3A%20For%20%60price_type%3A%20,option%20to%20get%20actual%20prices)[\[9\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=,Returns%20actual%20price%20from%20provider). Make sure this hook is the only place handling shipping rates in the front, and it’s working exclusively through Medusa’s API.

* **Error Handling & Loading States:** Ensure the UI properly handles slow responses or errors in shipping rate fetching (e.g., show a “Calculating rates...” state, which we partially have by disabling the pay button until rates are in[\[38\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=,is%20updated%20with%20shipping%20cost)[\[39\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=,workaround%2C%20not%20a%20UX%20solution)). This isn’t directly an architecture issue, but it improves UX consistency. The **20-second timeout** in tests for the pay button[\[20\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=1.%2020,E2E%20Tests) indicates our flow can sometimes be slow. A canonical solution would be to implement clearer loading states or even allow the user to click “Place Order” and then show a waiting indicator while shipping and tax finalize behind the scenes. (This could be complex with Stripe Elements, but it’s worth considering UX improvements as part of making the system feel robust.)

* **Fulfillment Module Alignment:** Verify that our EasyPost provider fully implements the Medusa fulfillment provider interface (methods like validateFulfillmentData, calculatePrice, createFulfillment) correctly[\[40\]\[41\]](file://file_00000000d3e4720ca1bb39f847ce3518). The documentation we have shows we’re persisting shipment data in validateFulfillmentData and using it in createFulfillment, which is exactly how Medusa expects it[\[42\]\[43\]](file://file_00000000d3e4720ca1bb39f847ce3518). So the backend side is canonical. The roadmap item here is mostly to **document and test** this thoroughly: simulate an order fulfillment in the Medusa Admin and ensure a label is purchased and tracking is updated as expected. This guarantees our backend logic is solid, so the frontend doesn’t need any hacks for shipping after an order is placed (it shouldn’t – the admin or automated workflows handle it).

**4\. Improve the Payment Workflow:**  
Our Stripe payment integration is mostly by the book (using Payment Collections and Stripe Elements). A few improvements to consider:

* **Avoid Duplicate PaymentIntents:** We already implemented a check to reuse an existing Stripe payment session if one exists for the cart[\[44\]](file://file_00000000a6a8722fae796b92119c5d66#:~:text=)[\[45\]](file://file_00000000a6a8722fae796b92119c5d66#:~:text=%2F%2F%203,%7D%29%20%7D). This follows Medusa v2.12+ recommendations[\[46\]](file://file_00000000a6a8722fae796b92119c5d66#:~:text=,one%20to%20avoid%20duplicate%20PaymentIntents). Continue to enforce this to prevent the “Could not delete all payment sessions” error[\[47\]](file://file_00000000a6a8722fae796b92119c5d66#:~:text=,%28500%20Error). This is a canonical fix as per Medusa docs – we should keep this pattern whenever creating payment sessions.

* **Order Completion Race Condition:** As mentioned, remove the 2s redirect fallback and replace it with a more deterministic approach. This could be implemented as follows (guidance for the AI agent or developers):

* After stripe.confirmPayment() indicates success, attempt POST /store/carts/{id}/complete (our completeCart() call). If it succeeds, we immediately have an order – proceed to success page.

* If completeCart responds with an error or times out, it likely means the payment webhook will handle order creation. In this case, enter a “pending” state on the frontend: display a message like “Payment received\! Finalizing your order, please wait…”. In this state, periodically poll an endpoint to check if the order exists. We could poll GET /store/orders?cart\_id={id} (if such filter exists) or use the payment\_intent ID (which we have) to search our backend for an order with that payment ID in metadata (we might store Stripe PI ID in order metadata via the webhook).

* Poll for, say, up to 30 seconds. If the order appears, redirect to success page. If not, show an error with instructions to contact support (and we monitor manually). This way, the user isn’t abruptly redirected without confirmation. This approach treats Medusa’s eventual consistency (via webhook) properly, at the cost of a bit more complexity in frontend logic. It’s a better pattern than a blind timeout and aligns with a **robust, user-friendly architecture**.

* **Frontend Stripe Elements Mounting:** Ensure that environment variables for Stripe keys are handled in the recommended way. We solved a bug by using a .env.production file to inject NEXT\_PUBLIC\_STRIPE\_PUBLISHABLE\_KEY at build time[\[48\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=3.%20Build)[\[49\]](file://file_000000003f0c720cbbd15f3cc3bde988#:~:text=available%20at%20runtime,secrets%20don%27t%20work%20for%20these). This is fine. We just need to document that clearly and ensure no one tries to use runtime secrets on the client. This is already done, so just keep it as-is (canonical approach is indeed to use Next’s public env for Stripe public key).

* **Testing and Edge Cases:** Re-run all checkout scenarios after refactoring: normal purchase, declined card, 3D Secure card, free checkout (if applicable), etc. Medusa recommends using a **Manual Payment** for $0 carts[\[50\]](file://file_00000000a6a8722fae796b92119c5d66#:~:text=Empty%20Cart%20Total%20,Error) – make sure our frontend handles that scenario (e.g., if cart.total is 0, perhaps skip Stripe and call completeCart directly with a dummy payment method). These are edge cases but part of making the integration canonical and foolproof.

**5\. Remove Workarounds and Anti-Patterns:**  
As we refactor, target each known workaround:

* **Hydration Guard:** If we implement server-side cart loading or otherwise ensure the cart state is ready on first render, we can drop the isMounted check and just render immediately. This may involve using Next.js 13 App Router features or simply not reading localStorage during SSR. Another way: we could store the cart ID in a cookie and configure Medusa’s cart endpoints to accept a cookie (Medusa can attach a cart to a cookie token if using the built-in mechanism, though by default that’s for session-based carts). However, since our approach is stateless (explicit cart IDs), SSR fetching is the straightforward solution. After migrating, test that navigating directly to /store/cart shows the cart without React hydration warnings.

* **State Duplication:** Any state that’s stored in multiple places (e.g., both Medusa and local) should have a single owner. For example, we persist cartId and cart items in localStorage for persistence across visits[\[51\]](file://file_0000000005bc722f8de4eb7ce1ca362e#:~:text=%60%60%60typescript%20partialize%3A%20%28state%29%20%3D,). That’s okay, but on app startup we should always validate that against the backend (e.g., if the cart was already converted to an order elsewhere, our frontend should detect that and not treat an old cart ID as a valid cart). Consider adding a check on initialization: fetch the cart by ID; if it’s not found or already completed, clear local cart state and start a new cart. This keeps the frontend state clean and avoids any weird edge cases. Medusa’s docs emphasize using the backend to validate any client-side cached state like this.

* **Logging and Monitoring:** Canonical architecture includes good observability. Our deployment guide notes that we log to a file and use PM2, etc.[\[52\]](file://file_000000000e4c71f59055adb367dfbfe2#:~:text=Viewing%20Medusa%20Application%20Logs)[\[53\]](file://file_000000000e4c71f59055adb367dfbfe2#:~:text=View%20Medusa%20application%20logs%20,app.log). Continue to leverage that for debugging. Ensure that our refactored code logs important events (e.g., “\[checkout\] Order polling started for cart XYZ” or an error if tax calculation fails). This will help catch any new issues introduced by changes. A well-architected system is not just clean in code but also transparent in operation.

* **Documentation Updates:** As we make these changes, update our internal docs (CHECKOUT\_FLOW.md, etc.) to reflect the new, simplified flow. For instance, if we remove the completion timeout, document how order finalization is handled. If we implement SSR cart loading, note that in the architecture. Keeping documentation in sync is part of maintaining a canonical architecture, so future developers (or AI agents) understand the intended design and don’t reintroduce anti-patterns.

**6\. Align with Medusa Updates:**  
Medusa is actively developing, so a part of the roadmap is to stay updated with the latest best practices from the official Medusa docs:

* **Medusa Modules v2:** Ensure our custom modules (tax and fulfillment) are compatible with the latest Medusa versions. For example, Medusa might introduce a refined Tax API or improve performance on cart retrieval with taxes. We should periodically audit the release notes and upgrade guides. A canonical architecture remains canonical only if it evolves with the platform’s improvements.

* **Testing Workflows:** If Medusa offers any testing utilities or recommended e2e flows (they mention a testing library or perhaps improved error messages for tax/shipping), incorporate those. For instance, our known issues table for Stripe Tax is comprehensive[\[35\]](file://file_000000001078720c85dc537ad8139c14#:~:text=,Ensure)[\[54\]](file://file_000000001078720c85dc537ad8139c14#:~:text=,only); checking those off with each Medusa upgrade ensures we haven’t reintroduced an old bug.

* **Consider Medusa Cloud or Cloudflare Workers Limits:** One reason we had to use Cloudflare Workers and a tunnel was to avoid CORS/hairpin issues. If Medusa provides a more seamless deployment or if Cloudflare improves worker networking, adapt accordingly. The architecture should remain as simple as possible – if in the future we can host the Next.js frontend on the same domain as the backend (or use Medusa’s upcoming Cloud offering), we might remove some layers (like the tunnel) to streamline the setup.

**7\. Testing and Validation Phase:**  
After implementing the above, thoroughly test the entire flow:

* **Checkout Flow Regression Test:** Follow the manual test checklist we have for Stripe Tax[\[55\]](file://file_000000001078720c85dc537ad8139c14#:~:text=Manual%20Test%20Checklist) and add more cases: different addresses (tax vs no-tax states), changing address mid-checkout, refreshing the page at various stages (to ensure state persists correctly via backend), etc. The frontend should always recover by fetching the latest cart from Medusa.

* **Edge Cases:** Simulate network failures or slow responses to ensure our new solutions work. For example, intentionally do not call completeCart and see if our polling detects the order from the webhook. Or fail the tax calculation by providing an invalid address and see that the error is handled (perhaps Medusa will return tax\_total: 0 or an error – ensure the frontend surfaces it gracefully, e.g., “Could not calculate tax for the given address”). A robust architecture accounts for these failure modes cleanly.

* **Performance:** Measure if the refactor improved performance. Removing unnecessary calculations and using SSR for initial data can reduce time to interactive. Also ensure that moving more logic to backend doesn’t overload the server – our Redis and Postgres should handle the extra reads, but just verify no significant slowdowns in API responses. If any are found, we may add caching (Medusa’s caching or our Cloudflare caching for certain GET requests).

* **Admin & Post-Order Flows:** Verify that everything still works in the Medusa admin: order details should show the correct tax breakdown (they should, since we commit the transaction and store tax lines on the order). The admin and fulfillment team should be able to see taxes, create fulfillments (using our EasyPost module) and trigger Resend emails if needed. These backend processes rely on the data our checkout collects, so if checkout is solid, these should be as well. Still, test creating a fulfillment on a new order to ensure the label is generated and tracking webhook updates the order status (per our EasyPost webhook flow[\[56\]](file://file_000000000e98720c8b4a62fdde699839#:~:text=Webhooks)[\[57\]](file://file_000000000e98720c8b4a62fdde699839#:~:text=,Hookdeck%20receives%2C%20transformation%20verifies%20signature)).

By following this roadmap, we will gradually eliminate the “split-brain” anomalies in our system. The end state will have **clear separation of concerns**: the Medusa backend as the authoritative source for all commerce logic (pricing, tax, shipping, payments, emails), and the Next.js frontend as a streamlined interface that **only handles presentation and input**. This mirrors the canonical architectures in Medusa’s examples (such as the Avalara integration and official Next.js starter) and will make our codebase more maintainable, scalable, and aligned with community best practices.

Ultimately, this refactor will remove the need for brittle workarounds, reduce the surface for bugs, and make future updates (both to our code and Medusa itself) much easier to manage. Following Medusa’s docs and patterns closely is our guide – whenever in doubt, we’ll prefer the approach that **centralizes logic in the backend** and keeps the frontend agnostic of business rules, thereby avoiding the pitfalls we encountered with our initial implementation.

With this roadmap executed, our Medusa-Next.js stack will be on a solid, canonical footing moving forward, and the Stripe Tax integration (as well as shipping, payments, etc.) will behave as a first-class citizen in the Medusa ecosystem – no hacks required.
